# Evidence: M3.7, public memories

## Scope

Authorized by the owner on 2026-11-03 (issue #52, draft pull request #53). Memories, the existing `memory` entry kind written in the M3.6 Memories Studio, become publishable and readable: the studio's publication review, Publish…, Unpublish…, and confirmed changes to a published memory, and the anonymous page `/memories/<slug>` in the approved V4.4 `Memory` layout. **Local only**: nothing is deployed, the public-reads switch is never enabled on a reachable host, and gates G1 to G8 stay open (#47).

Owner constraints applied: the established ADR 0006 workflow only (one `ct1` token, one engine), a memory wrapper that checks its own kind, no new entry kind, no ratings, favourites, or artwork, no Memories directory, no memory cards on the Home, no translations, issue #44 untouched. No migration, no dependency, **no ADR change**: ADR 0006 § 1 already lists a memory's atoms ("Memory details": the remembered-when text, each music link, the order of the links), and every rule here is that text carried out.

## Publication and confirmed save

- **Publishing** ([`memory-publishing.ts`](../../src/modules/journals/memory-publishing.ts)): `previewMemoryPublication` returns the review (title, "when", the writing as plain text, the songs with the words and links the page shows, the address, the status being left) and a `publish` token from `previewPublication`, in one read-only snapshot; `publishMemoryVersion` passes the token to `publishLanguageVersion`. Both check the kind against `memories` first; the album-journal wrappers check `album_journals`. Draft and Private take the same path; a memory with no songs still needs its token.
- **Unpublishing** is `setMemoryPrivacy` (M3.6): Private or Draft, no token (R4); the studio asks first.
- **The confirmed save** ([`memories.ts`](../../src/modules/journals/memories.ts)): `saveMemory` verifies a supplied token before the transaction, locks the entry joined to `memories`, refuses a deleted memory and a stale version, validates against the stored rows (`prepareMemoryChange`: unsupported text, album links, unknown or archived recordings), then calls `requirePublicChangeConfirmation` with the proposed change. Only then does it write the title and body, the "when", and the recording links (inside `saveMemory` itself, so the owner-approved writer list is unchanged), bump the version, and check with `assertWrittenAsPredicted` that a reader would see exactly what was confirmed. `previewMemoryChange` makes the same refusals in a read-only snapshot; `previewMemoryPublicChange` adds the songs' names, before and after, read in the same snapshot. The M3.6 refusal `memory_published` is gone.
- **The interface**: Publish… in the margin (waiting until changes are saved), "Publish this memory?", Unpublish… with Private or a draft, "Update the published memory?" with each change before and after (the songs as one change, "The music"), and "Take this away from the published memory?" before a save that only removes a song or the "when" (ADR 0006 § 5: no token, but the interface asks first). Each preview action is alone in its file; only the two memory dialogs name the token and send it from their confirm control.

## Disclosure and fingerprint guarantees

The memory's public atoms ([`surface.ts`](../../src/modules/publication/surface.ts)), public while some version is published and the entry is not deleted:

| Atom | Key | Change classification |
| --- | --- | --- |
| Title, writing (and the empty opening and margin note) of each public version | `version\|<locale>\|<field>` | any difference is an edit (shorter, white space only, cleared) |
| The "when", only when it has words (the page shows nothing for a blank one) | `memory\|when` | set: addition; changed: edit; cleared: removal |
| Each music link | `memory\|link\|track:<id>` (or `album:<id>`) | added: addition; removed: removal |
| The order: one atom per ordered pair ("a before b") | `memory\|order\|<a>\|<b>` | any reorder adds a pair; removing a link only removes pairs |

So "a music link is the atom (link id, relative rank)" (ADR 0006 § 5) holds exactly: removing a link from anywhere is a strict subset, renumbering changes nothing, and adding or moving one always asks. Recording ids are lower-cased first, so one recording spelled two ways is one link. A public memory must keep a title and writing (`nothing_to_publish`), and publishing refuses a memory without a title (ADR 0006 § 4, step 6).

The publication fingerprint binds the version's text atoms, the address, the "when", the ordered link ids, and the state stamp, as for every kind. The disclosure also carries `memoryMusic`, the songs as the page names and links them: **shown, not bound**, because catalog wording is the documented gap C11 (ADR 0006 § 2), not something this milestone may silently change. A test shows a recording renamed after the review does not make the token stale; that is recorded under G8, not accepted as harmless.

## Public memory reading contract

- `/memories/<slug>` is decided in [`src/proxy.ts`](../../src/proxy.ts) before the page renders, by `routeMemoryRequest`, which shares `routeEntryRequest` with the album journal: the switch, the method (`405` with `Allow: GET, HEAD`), the slug's form, then `resolvePublicSlug(db, "memory", slug)`. Draft, private, deleted, restored, unpublished, retired, never-public previous, malformed, unknown, and album-journal addresses answer the identical unknown-address `404`; a previous address of a public memory answers a `no-store` `308` to `/memories/<current>`, with no host reflected.
- The page ([`(memories)/memories/[slug]/screen.tsx`](../../src/app/(memories)/memories/[slug]/screen.tsx)) resolves the address again behind the switch, reads `getPublicMemory` through the reading entry point, and renders in one pass (`instant = false`). The read model ([`public-memory.ts`](../../src/modules/publication/public-memory.ts)) starts every statement from the predicate or the served address; it returns the slug, the version's language and publication date, the title, the body, the "when", and the music, and no identifier, status, deletion state, or reflection.
- Metadata: the memory's title, a fixed description ("A memory in a personal music journal."), the canonical address from the site's own origin, Open Graph `article`, no image, no excerpt. Not-served addresses get the not-found view's metadata.
- Caching: `no-store` on every response (`next.config.ts` covers `/memories/:path*`); the build holds an empty, parameterised shell (`[slug].html` empty, `isFallback`) and no memory data; the sitemap lists served memory addresses only.

## Related music

From [`memory-music.ts`](../../src/modules/publication/memory-music.ts), one function for the review and the page: each link in the memory's order with its title and credited artists (the recording's, or for an album link the album's credits). A credited artist links to `/artists/<address>` only if it already has a page (`publicArtistAddresses`; memories open none, ADR 0006 A5); an archived artist is plain text. A recording names one album, the one with a served journal when there is one (linked to that journal), otherwise its earliest (plain text). An archived recording is still named. No database or MusicBrainz identifier leaves the function. Track reflections of album journals are never read.

## Hosted-release requirements

Nothing here closes a gate; G1 to G8 stay open and #47 stays open.

- **G8 (C11) for memories.** A public memory's music is catalog wording that changes without a confirmation: a recording's title or credited artists, an artist's name, an album's title, and which album a recording names. Its links appear and disappear as other journals are published or unpublished (each of those is confirmed, and a link only ever leads to a public page). Track renames, credit changes, and artist renames are not serialized with memory publications. To be resolved, or an independently verified safe alternative recorded, before the first hosted public page.
- **G1, G2, G5.** The memory route has the same local evidence as the album journal's and the artist page's (statuses, identical `404`s, `no-store`, the switch), and needs the same proof on the hosted configuration. The framework's repeated-slash `308` (A2) applies to `/memories//x` as to every address.
- **G3, G4.** `memories` and `memory_music` are now part of a public surface: out-of-process writers of them join G3's inventory.
- **G7.** The four reviews above are this milestone's; G7 needs the review of the whole public surface before hosting.

## After the owner's review of the report (2026-11-04)

- **Removals inside a mixed save.** "Update the published memory?" listed the additions and edits and only said, in general, that removals went with them. It now names each removal under "Taken away from the published memory" (derived from the editor's saved state, display only: no token, command, or delta changed), with a browser check of a title edit and a cleared "when" in one save (`14-edit-and-removal`).

- **A focused Publication review** (independent, read-only, at `8b8adb5`) of the preview, the checked publish, confirmed updates, unpublication, the kind checks, the fingerprint, the `memory_music` writes, the order's confirmation, removals, tokens, and concurrency: no Critical, High, or Medium finding. It tried every ordered-list input it could think of (reorders, a swap with a removal, a replaced song, duplicates and mixed case, archived recordings, album links, an empty list, renumbering) and found none that changes what a reader sees without a token. One **Low**, fixed: a stale editor that still showed a memory as private (another tab had published it) saved a removal without asking, because a removal needs no token. The save now carries the status the editor showed (`expectedStatus`) and is refused as `status_changed`, in the save and in its preview, when the memory's status changed meanwhile; the editor refreshes and the next save asks. Tests: an integration test in both directions, and a browser step with a stale tab. Two **Info** items: Cmd/Ctrl+S could open a second review over the removal dialog (fixed); the kind check is an unlocked read before the token's MAC, as in the album wrapper (kept: no lock is held, so ADR 0006 § 4, step 2 holds).

## Owner decisions after the M3.7 review

- **Removals in the album journal's editor: decided.** The owner does not accept the M2.3 behaviour (an unflag, a cleared reflection text, or a cleared rating saved without asking) as an exception to ADR 0006 § 5, and the ADR is not changed. Tracked in issue #54, **required before any hosted launch** (#47). Not changed in this pull request.
- **The "when" per language: decided for now.** It stays shared and unchanged, and no migration is authorized. A future author-written "when" per language is recorded, with its conditions, in [Data Model § Open questions](../data-model.md#open-questions), item 3.

## Remaining limitations

- No public-layout preview of a memory inside the studio (as for album journals); the publication review is the preview.
- Some concurrency tests hold the entry lock with raw SQL standing in for the other command; the two-confirmed-saves race does not observe the lock wait.
- A state change between the proxy's decision and the render is answered by the page's own not-found or redirect; untested here, as on every public page.
- Behaviour over real HTTPS is not verified (#11).
- Issue #44 (the album journal without JavaScript), #50, and #51 are unchanged.

## Deferred

A Memories list and "All memories" / "Next memory", memory cards on the Home, artwork for memories (and with it the artwork guard for memories, a condition recorded in M3.2), memory translations, and the language selector.
