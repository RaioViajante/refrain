# Evidence: M3.3, artist photography from Wikimedia Commons

**What this is.** A record of what M3.3 built, how it was checked, and what was not. It describes the branch `feat/m3-3-artist-photography` (issue #38), started from `main` at `483962b3c5d53c662bf2ba92656831956c36e0e4`. Every test ran against the **disposable test database** and a **local provider mock**; the owner's development database was not touched. Everything shown is synthetic (`[Test] …`, `Test_…` files, generated images). **Nothing is deployed, no public page shows a photograph, the public-reads switch is on only in the tests' own public server, and gates G1 to G8 stay open.**

## Baseline and the schema decision

`artists` already had `photo_url`, `photo_credit`, `photo_license`, `photo_source_url`, and `CHECK (photo_url is null or (photo_credit is not null and photo_license is not null))`; no code wrote them. They can hold a photograph safely in one strict form, as M3.2 does for covers. They cannot record **which version** of a Commons file the author reviewed or **when** it was approved: Commons files can be overwritten, so a later rights review could not reconstruct what was approved, and the image could change unseen.

The owner was asked and **approved one additive migration** (`0005`, through `/refrain-db-change`): nullable `photo_file_sha1`, `photo_file_timestamp`, `photo_chosen_at`; `artists_photo_file_sha1_check` (40 lowercase hexadecimal characters); and `artists_photo_provenance_check`, which ties **each** of the three to `photo_url`. The CHECK first proposed to the owner (`(photo_url is null) = (all three null)`) would have accepted a photograph with only some provenance; the integration test that sets each column to null in turn caught it before the migration was committed, and it was regenerated with the per-column form, which is the owner's stated intent ("set exactly when `photo_url` is").

Verified on the disposable database: migrations `0000`–`0004` applied, synthetic rows inserted, then `0005`: with a row holding a photograph written by `psql`, the migration fails as a whole (`artists_photo_provenance_check … is violated by some row`) and the table keeps its four original photo columns; without it, it applies and every row survives unchanged; partial provenance and an uppercase SHA-1 are refused by name. `pnpm db:check` passes and `pnpm db:generate` reports no changes. No backfill; nothing was written to the owner's database (applying `0005` there is the owner's step, [Development](../development.md#artist-photographs-m33)).

## Identity and selection

- **Nothing is chosen for the author.** A search result and a suggestion lead only to a review; only **Use this photograph** on the review writes. No photograph is imported, replaced, or chosen automatically, and no rank or popularity counts as identity.
- **Wikidata is a lead.** For an artist linked to MusicBrainz, the one Wikidata item with that MusicBrainz ID (two items, or none: no suggestions) gives its image (P18) and the files that say they depict it (P180). The page says: "That is a lead, not proof: check that each photograph really shows them." Search results say: "A search finds words, not people." Candidates are announced by their file ("Candidate: …"), never as a photograph of the artist.
- **Artist and photograph stay separate.** The photograph is seven columns of the artist row, written only by the photo commands; the manual form cannot write them (an integration test), and editing the artist never touches them, nor the photograph the artist's details.
- **Exactness.** The review carries a SHA-256 of the plan (file, SHA-1, upload time, addresses, license, credit). On approval the server asks Commons again (bypassing the cache), assesses the file again, and writes only if the fingerprint matches; otherwise `stale`. A file that is no longer usable is `photo_not_usable`; a file that is gone is `provider_not_found`.
- **No silent replacement.** Setting and removing both send a fingerprint of the stored photograph the author saw, compared under the artist's row lock (`FOR NO KEY UPDATE`). Two changes from the same view: one wins, the other is refused (a test on two real connections). Archived artists are refused.
- **The photograph on file is checked.** The photograph page compares it with Commons: unchanged; a new version (the SHA-1 differs; the frame would show the new version, so the page asks for a new review or a removal); changed credit or license; gone; no longer usable; or Commons unreachable.

## License and attribution

The policy is in code and tested ([`license.ts`](../../src/integrations/wikimedia-commons/license.ts), [`assess.ts`](../../src/integrations/wikimedia-commons/assess.ts)):

- **Accepted:** CC0 1.0; Commons' public-domain mark (`pd`, `Copyrighted: False`, no deed); CC BY and CC BY-SA 2.0, 2.5, 3.0, 4.0 (generic, unported, international). The short name, the code, and the deed address must agree, and attribution must be marked required for CC BY and BY-SA.
- **Refused (fail closed):** non-commercial and no-derivatives variants, jurisdiction ports, GFDL-only and every other license, files marked non-free, disagreeing metadata (how an ambiguous multi-licensed value is caught), deletion nominations, files with no named creator or "Unknown author", credits over 300 characters or that still read as markup, formats other than JPEG and PNG, files under 600 × 400 px, and any file whose addresses differ from Refrain's rebuilt ones. A refused file is never offered and its thumbnail is never loaded; the review lists the reasons in words.
- **Who is credited.** The file's own `Attribution` field when it has one (it replaces Artist + Credit), else `Artist`, reduced to plain text. Never the uploader. The review shows the creator separately when the credit is a designated attribution, and Commons' source note.
- **What is shown.** "Photo: [credit] · [license, linked to its deed] · via Wikimedia Commons" (no second "Photo:" when the attribution has one), and **Photo details**: the work's title linked to its page, the credit, the source, the license (with the share-alike note), and "Resized, and cropped to fit the frame. No other changes." Every link is built from the file name or a fixed table; extended-metadata HTML is never rendered.
- **Rights the license does not cover.** Every review says "A free license covers the photograph itself, not the people in it", and shows Commons' personality-rights warning when the file has one. Public-domain status that depends on the country is a hosted-release item.

## Image security, caching, and privacy

- **Only the server talks to Wikimedia**, after authorization; an anonymous request causes none (the mock's log). Requests carry the typed words reduced to letters, digits, spaces, and `' & . , -` (no `insource:`, regular expressions, or quotes reach CirrusSearch), a file name that passed the strict shape, an MBID, or an item id. Never an artist id, a session, a cookie, or writing.
- **No arbitrary addresses.** Base URLs are fixed unless pointed at a loopback mock; no redirect is followed; the stored form is parsed strictly and addresses rebuilt from the file name; the stored values are never rendered as addresses. The studio's CSP allows images only from `thumb.wikimedia.org` in addition to M3.2's hosts; the public pages' CSP is unchanged (no Wikimedia), and the Cover Art Archive restrictions are untouched.
- **No image bytes stored.** Thumbnails load in the author's browser with `referrerpolicy="no-referrer"` (and the studio's `Referrer-Policy: no-referrer`): Wikimedia learns the viewer's address and the file, never the page. No proxy was built.
- **Stable layout.** The frame is a fixed 4:5 box with the fallback inside; the image covers it once loaded. A thumbnail that fails is removed (also when it failed before hydration), so the fallback is all that remains. A browser test compares the frame's size loaded and failed.

## Public pages (gate G8)

No public page shows an artist photograph: the album journal's read model selects artists' names only. A structural test fails if the Publication reading module, any file under `src/app/(public)`, the sitemap, or `robots.txt` mentions a photo column or the Wikimedia integration, and an integration test shows a published album journal is byte-identical whatever its artists' photo columns hold. A photograph change therefore reaches no reader, and **G8 is not widened**. No photograph guard is built, deliberately: one is needed with the first public surface that shows a photograph, and it would hold several entry locks, which [ADR 0006 A3](../decisions/0006-publication-decision-and-acknowledgement.md#a3-the-artwork-commands-take-entry-locks-then-a-catalog-lock) says needs its own decision ([Security § Deployment gate](../security.md#deployment-gate), item 7).

## Hosted-release obligations

Recorded in [Security § Deployment gate](../security.md#deployment-gate), item 7, and not implemented: the per-photograph license review (credit, license and link, source, changes, share-alike), the check that each shown photograph is still the approved version, personality and privacy rights, country-dependent public-domain status, the removal procedure for a rights holder or a person shown, the third-party request and the privacy notice (or an image proxy), the public CSP widened only with the first public photograph, and a photograph guard (G8) with its own lock-order decision. The M3.2 obligations (artwork rights, a shared MusicBrainz limit, minimum CSP hosts, image privacy, the removal path) are unchanged.
