# Evidence for M1.3C: academic verification, recovery, and browser tests

> **Later state (added 2026-11-05, M4.2).** This page records M1.3C as it was run; its results are not rewritten. The current academic evidence, with the requirements matrix, an ER diagram, the SQL, and the demonstration runbook, is [Evidence: M4](m4.md).

**What this is.** A record of runs of the real application, through a real browser, against real PostgreSQL, and how to repeat them. It maps each academic requirement ([Requirements](../requirements.md#mandatory-requirements), AC-01 to AC-06) to the screen or operation that shows it, the tables involved, the query, what you should see, and the check that was executed. It does not mark the requirements verified: that waits for the author's review and the clean-database rehearsal (M4).

**What it is not.** Every record below is a synthetic `[Test] E2E …` fixture in the **disposable test database**, made through the Studio's own forms by the browser tests, with a synthetic author. Nothing of the author's writing, nothing in the development database, and nothing of the owner's account was used. The results are the state *after* the run described in [Run record](#run-record).

## Reproduce it

```sh
pnpm db:test:down && pnpm db:test:up      # a clean, disposable test database
E2E_KEEP_DATA=1 pnpm test:e2e             # builds, runs the browser suite, keeps its records
docker compose --profile test exec -T postgres-test psql -U refrain_test -d refrain_test   # then run the SQL below
pnpm db:test:down                         # discard everything
```

`E2E_KEEP_DATA` keeps the synthetic records after the run so that `psql` can read them back (the application's server has been stopped by then: the rows are in PostgreSQL, not in the application). Without it, the suite removes its records. Details: [Development § Browser tests](../development.md#browser-tests). The `psql` command above targets the test container only; never point it at the development database to repeat this with synthetic data.

## "Delete" means two different things here

The product deletes writing by **moving it to Recently deleted**, which is an `UPDATE entries SET deleted_at = now()`. The row, its language versions, its text, and its slug **stay in the table**; nothing is physically deleted, and the journal can be restored ([ADR 0002 D4](../decisions/0002-domain-model-decisions.md), [ADR 0005](../decisions/0005-restoring-deleted-journals.md)). Nothing in M1.3C deletes a journal's row, and there is no "Delete now" yet.

A real SQL `DELETE` exists for **catalog records that nothing refers to** (artists, albums, tracks), and PostgreSQL refuses it for any record that writing or credits refer to (`ON DELETE RESTRICT`). The browser test `catalog.spec.ts › deletes a record nothing refers to, for real, and refuses one that is in use` performs both. This is the academic `DELETE` of AC-03, and it is not a soft delete.

## The example: an album, its credited artist, linked tracks, and a private journal

Made by `academic.spec.ts` through the Studio (an artist; an album credited to it, first released 1994; two tracks created on the album; a journal about the album, made private), and read back with one query across six tables. All names are synthetic.

```sql
select al.title as album, coalesce(aa.credited_as, ar.name) as artist,
       et.position, t.title as track, o.status, e.deleted_at is not null as deleted
  from albums al
  join album_artists aa on aa.album_id = al.id
  join artists ar       on ar.id = aa.artist_id
  join album_editions ed on ed.album_id = al.id and ed.is_reference
  join edition_tracks et on et.edition_id = ed.id
  join tracks t          on t.id = et.track_id
  join album_journals j  on j.album_id = al.id
  join entries e         on e.id = j.entry_id
  join entry_texts o     on o.entry_id = e.id and o.is_original
 where al.title like '[Test] E2E % Academic Album'
 order by et.position;
```

```text
               album                |                        artist                        | position |                track                 | status  | deleted 
------------------------------------+------------------------------------------------------+----------+--------------------------------------+---------+---------
 [Test] E2E 181165cc Academic Album | [Test] E2E 181165cc Academic Artist (renamed in SQL) |        1 | [Test] E2E 181165cc Academic Track A | private | f
 [Test] E2E 181165cc Academic Album | [Test] E2E 181165cc Academic Artist (renamed in SQL) |        2 | [Test] E2E 181165cc Academic Track B | private | f
(2 rows)
```

The artist's name carries `(renamed in SQL)` because the last test of `academic.spec.ts` renames it with an `UPDATE` to show that a change in the database appears in the interface (AC-06). The journal is `private` and not deleted; it has no public page, because none exists yet.

How to read it:

- **AC-04.** The JOIN returns the album once per credited artist, with the artist's name and position. The Albums page runs the same SQL.
- **AC-05, aggregate.** `COUNT … GROUP BY` over a `LEFT JOIN`: 2 tracks for the example, 0 for albums without tracks. The credits are not joined into this query, so an album with several artists still counts each track once (a test covers it).
- **AC-05, subquery.** "Used in" counts the live entries that refer to each album. The Recovery album reads 3 because three journals were written about it (all restored or live). A journal in Recently deleted is not counted, which the page shows as 0 while it is there.
- **AC-05, `FILTER`.** The Desk's journal figures: 6 journals, 2 drafts and 4 private, none published and none deleted at the end of the run.
- **Recovery.** The three Recovery journals were each moved to Recently deleted and restored. The second one was published (`first_published_at` is set) before it was deleted; it came back **private**, with `published_at` cleared and its history kept. The third was a draft and returned as a draft.
- **RESTRICT.** A real `DELETE` of an album that a journal refers to is refused by PostgreSQL, even though the journal is soft-deleted or live: writing is never destroyed by a catalog delete.

## Database structure

`\d` of three of the tables, from the same database (the full schema is in [Data Model](../data-model.md) and the migrations):

```text
              Table "public.album_artists"
   Column    |   Type   | Nullable
-------------+----------+----------
 album_id    | uuid     | not null
 artist_id   | uuid     | not null
 position    | smallint | not null
 credited_as | text     |
Indexes:
    "album_artists_pkey" PRIMARY KEY, btree (album_id, artist_id)
    "album_artists_position_unique" UNIQUE CONSTRAINT, btree (album_id, "position")
Foreign-key constraints:
    "album_artists_album_fk" FOREIGN KEY (album_id) REFERENCES albums(id) ON DELETE CASCADE
    "album_artists_artist_fk" FOREIGN KEY (artist_id) REFERENCES artists(id) ON DELETE RESTRICT

            Table "public.album_tracks"
 album_id | uuid | not null
 track_id | uuid | not null
Indexes:
    "album_tracks_pkey" PRIMARY KEY, btree (album_id, track_id)
Foreign-key constraints:
    "album_tracks_album_fk" FOREIGN KEY (album_id) REFERENCES albums(id) ON DELETE CASCADE
    "album_tracks_track_fk" FOREIGN KEY (track_id) REFERENCES tracks(id) ON DELETE RESTRICT

            Table "public.album_journals"
Indexes:
    "album_journals_pkey" PRIMARY KEY, btree (entry_id)
    "album_journals_one_featured_idx" UNIQUE, btree (album_id) WHERE is_featured
Foreign-key constraints:
    "album_journals_album_fk" FOREIGN KEY (album_id) REFERENCES albums(id) ON DELETE RESTRICT
    "album_journals_entry_fk" FOREIGN KEY (entry_id, kind) REFERENCES entries(id, kind) ON DELETE CASCADE
```

The pattern is the project's rule: a link row belongs to its album and goes with it (`CASCADE`), while anything authored refers to the catalog with `RESTRICT`, so a catalog `DELETE` can never remove writing ([AGENTS § 4](../../AGENTS.md)).

## Recovery: what is asserted and where

The owner-accepted policy ([Roadmap](../roadmap.md#follow-ups-from-the-m13b-review), [ADR 0005](../decisions/0005-restoring-deleted-journals.md)) is what each row checks.

| Policy | Where it is asserted |
| --- | --- |
| Draft returns as draft; private as private; published as **private**; for every combination of two language versions | [`restore.integration.test.ts`](../../src/modules/journals/restore.integration.test.ts) (the nine-combination case); `recovery.spec.ts` |
| The writing (every paragraph, line break, opening sentence) and `entries.version` are unchanged | The same; `journal.spec.ts` and `recovery.spec.ts` compare the exact text after the restore; `studio-actions.http.test.ts` |
| `first_published_at` on the version and on the entry is preserved | The integration test, the HTTP test, and `recovery.spec.ts` (the `2026-01-01` history of the journal that had been published) |
| Slugs, `was_published`, and `is_current` are unchanged; a previous slug redirects only when the entry is public again; a published slug is not reassigned | The integration test (slug rows compared before and after; `resolvePublicSlug` before, after, and once the author publishes) |
| A restore never publishes; public queries show nothing after it | The integration test (public queries before deletion, while deleted, after the restore, and after an explicit publication); the browser test (no published version remains) |
| Not authorized, not the author's session, forged or expired sessions, no `Origin`: refused, nothing changes | `studio-actions.http.test.ts` (a deleted journal, so a restore that got through would show); `studio-entry-points.test.ts`; a mutation that ignored the authorization result failed the HTTP suite |
| A journal that is not deleted, an unknown id, a malformed id, an entry of another kind: refused with a fixed code | Integration and HTTP tests |
| A repeated or concurrent restore: one succeeds, the rest are refused, nothing changes | The integration test (a second restore); the real-connection race (eight at once); `recovery.spec.ts` (a stale tab) |
| Atomic: a failure after the demotion rolls the demotion back | The integration test, with a trigger that fails the undelete |
| No permanent-delete control, no automatic purge, no "30 days" copy | `studio-actions.http.test.ts` (page text); `recovery.spec.ts`; the existing database-level test that no trigger or rule purges |

## Limitations

- **Verified only on synthetic data in the disposable database.** The development database, which holds the owner's account, was never used, and a restore of the owner's real data was not tested.
- **Plain HTTP only.** The browser tests do not exercise HTTPS, the `Secure` cookie prefix, or a proxy. Chromium only.
- **AC-05's "written track reflections per album journal" is not demonstrated in the interface**, because track reflections are not built. The Desk query that counts them exists and is tested (`listAlbumJournalProgress`), and the Desk shows each journal's "n of N tracks written" as 0 of the album's track count. The aggregates shown above are the track count per album, the journals by status, and the usage subquery.
  - *Update, 2026-11-05 (M4.2):* track reflections were built in M2.2, and `academic.spec.ts` now saves one and checks that the Desk reads "1 of 2 tracks written", as a count in SQL does ([Evidence: M4](m4.md#ac-05-a-subquery-or-an-aggregate)).
- **The academic `DELETE` is shown on an unreferenced catalog record.** The `DELETE` of an entry through "Delete now" does not exist yet; the demonstration script's step 7 waits for M2. Soft deletion is not a `DELETE`, and is not presented as one.
- **Catalog edits are last-write-wins.** Two tabs can overwrite each other's named fields on an artist, album, or track; nothing in this evidence claims conflict protection for them ([Roadmap](../roadmap.md#catalog-edit-concurrency-last-write-wins)). Journal text is protected and tested.
- **The restoration of a "published" journal is set up directly in the database**, because no studio control publishes yet. The policy, not a user flow, is what is tested for that state.
- **"Verified" in the requirements table stays empty** until the author reviews this and the demonstration is rehearsed on a clean database (M4). Screenshots and recordings have not been captured here.

## Backup coverage

The schema has **22 tables** in `public`, plus `drizzle.__drizzle_migrations`. `pnpm db:backup:verify --compare-with` accounts for every one of them:

- **19 tables are compared**, each by row count and a digest over the full text of every row: `artists`, `albums`, `tracks`, `album_artists`, `album_tracks`, `album_editions`, `edition_tracks`, `track_artists`, `entries`, `entry_texts`, `album_journals`, `entry_slugs`, `track_reflections`, `track_reflection_texts`, `memories`, `memory_music`, `artist_journals`, `auth_users`, `auth_accounts`. Together they hold the writing and its status, publication history, deletion and versions; the slugs and their marks; the catalog; and the author's account with its password hash.
- **3 tables keep their structure but not their rows in a backup:** `auth_sessions` (live session tokens, which could be replayed), `auth_verifications` (one-time values; Refrain sends and uses none), and `auth_rate_limits` (sign-in counters). They hold no writing, no publication state, no slugs, and no credentials. The restore check requires them to come back **empty**, and the archive's table of contents has their definitions and no data entries.
- **The migration history** is compared by count.
- **A table in none of these lists fails the check**, so a table added later cannot be silently left out.

Rehearsed on the disposable test container with the browser suite's data: a deliberate one-character change to a language version's text, a flipped slug mark, and an unknown extra table each made the check fail, and the unchanged source passed. A backup of the owner's real database was not made, and its restore is untested.
