# Evidence for M1.3B: catalog and album-journal CRUD

> **Later state (added 2026-11-05, M4.2).** This page records M1.3B as it was run; its results are not rewritten. The current academic evidence, with the requirements matrix, an ER diagram, the SQL, and the demonstration runbook, is [Evidence: M4](m4.md). Since M1.3B, restore was built in M1.3C, and track reflections in M2.2; "Delete now" is still not built.

**What this is.** A record of one run of the real application against real PostgreSQL, and how to repeat it. It supports the rows of [Requirements](../requirements.md#traceability) for AC-01 to AC-06. It does not mark them verified: that waits for the author's review and the clean-database rehearsal (M4).

**What it is not.** Every name below is a synthetic `[Test] E2E …` fixture in the disposable test database, with a synthetic author. Nothing of the author's writing, and nothing in the development database, was used. The results are the state *after* the journey described below.

## The journey

Run through the production build (`next start`) in a headless browser, signed in through the real sign-in form:

1. Anonymous `/studio` lands on sign-in; a wrong password is refused in words; the right one opens the desk, with an `HttpOnly`, `SameSite=Strict` cookie.
2. Add an artist (a blank name and a malformed MusicBrainz id are refused with messages), then an album credited to it, with its reference edition.
3. On the album, create three tracks, move one, remove one (after a confirmation), and add it back: three rows in `album_tracks`, never duplicated.
4. Write a journal: an opening sentence and two paragraphs (one with a line break) containing literal markup. Save as a draft, leave, return, and find the text intact; edit and save again with Cmd+S.
5. A second tab saves first: the first tab's stale save is refused as a conflict, and its typed text stays in the box.
6. Make the journal private; try to delete the album (refused, in words); delete the journal (it moves to Recently deleted and is kept).
7. Check the pages at 390 px (no horizontal overflow), sign out, and open the journal's address (nothing private appears, also after "back").

The script is not part of the repository (it needs a Chromium build that the project does not depend on). The same behavior is asserted without a browser by the tests below.

## SQL results

```text
 en     | private | [Test] E2E First paragraph.+|          2 |       3 | t       | test-e2e-album | f
        |         | Second line of it.         +|            |         |         |                | 
        |         |                            +|            |         |         |                | 
        |         | <b>Not bold.                |            |         |         |                | 
(1 row)

-- A RESTRICT refusal: hard-deleting an album that a journal references
ERROR:  update or delete on table "albums" violates foreign key constraint "album_journals_album_fk" on table "album_journals"
DETAIL:  Key (id)=(6014a9ce-f680-4dff-8a71-fe1f5019ccfb) is still referenced from table "album_journals".
```

How to read it:

- **AC-04, JOIN.** `albums ⋈ album_artists ⋈ artists` returns the album with its credited artist. The Studio's Albums page runs the same SQL (`listAlbumsWithArtists`).
- **AC-05, aggregate.** `COUNT` with `GROUP BY` over a `LEFT JOIN` gives 3 tracks on the album, and would give 0 for an album with none. The credits are not joined into this query, so a three-artist album still counts its tracks once (a test covers it).
- **AC-05, subquery.** `used_in` is 0 because the journal was deleted at the end of the run; while it existed the page read "used in 1 entry" (asserted by an HTTP test).
- **AC-05, `FILTER` aggregate.** The Desk's journal figures. The one journal is counted as deleted, not by status.
- **AC-03, delete.** The journal is in Recently deleted (`deleted = t`) with its text, its `private` status, and its slug (never published, `was_published = f`) all kept. The last statement is a real `DELETE` refused by `ON DELETE RESTRICT`: an album that a journal references cannot be hard-deleted, even when the journal is in Recently deleted. A real `DELETE` of an *unreferenced* record is shown by the tests (`deleteArtist`, `deleteAlbum`, `deleteTrack`, and the HTTP journey).

## CRUD and the meaning of "delete"

| Entity | Create | Read | Update | Delete in the domain's sense | Real `DELETE` |
| --- | --- | --- | --- | --- | --- |
| Artist, album, track | Studio forms | Lists and pages | Studio forms | **Archive** (hidden from pickers, writing untouched), restorable | Only when nothing refers to it; otherwise refused as `in_use` |
| Album tracklist | Add or create a track | Album page | Move | Remove from the album (the track stays) | `album_tracks` and `edition_tracks` rows; refused for a track a reflection refers to |
| Album journal | Studio editor | View and edit pages | Studio editor, version-checked | **Move to Recently deleted** (`deleted_at`), recoverable | Not offered: "Delete now" and restore are not built; the restoration policy was decided by the owner afterwards ([Roadmap](../roadmap.md#follow-ups-from-the-m13b-review)) |

Soft deletion and archiving are the product's meaning of delete (ADR 0002, D4); the model is not weakened for the demonstration.
