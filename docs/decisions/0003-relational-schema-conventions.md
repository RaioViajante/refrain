# ADR 0003: Relational Schema Conventions

- **Status:** Accepted
- **Date:** 2026-10-31. Proposed with M1.2 (issue #4, pull request #5). The author amended slug retention and publication history in review, and accepted the amended decision the same day.
- **Scope:** How the first migrations represent ADR 0002, and the open questions from [ADR 0002](0002-domain-model-decisions.md#still-open-after-this-adr) and [Data Model](../data-model.md#open-questions) that the schema depends on. It refines ADR 0002 and changes none of its decisions.

## Context

ADR 0002 left three questions open, and the [Roadmap](../roadmap.md) asked M1.2 to settle the ones that affect the first migrations:

1. How enumerations are represented in PostgreSQL.
2. Whether a slug is released when an entry is permanently deleted.
3. Whether published language versions return as private when a deleted entry is restored.

The preliminary data model also left details to the implementation: the column-naming convention, and where publication history lives. Migrations are permanent once applied, so these are settled before M1.2 is merged.

The first proposal released every slug on permanent deletion, so that nothing title-derived would remain. In review, the author rejected that: a URL that once showed published writing must never lead to unrelated writing later. The author also asked for publication history per language version, kept separate from current visibility. Decisions 3 and 4 below are the amended, accepted versions.

## Decision

### 1. Enumerations are `text` with `CHECK` constraints

Entry kind, locale, visibility status, and artist kind are `text` columns with a named `CHECK` constraint listing the allowed values.

- The values are defined once, as TypeScript arrays in `src/db/schema.ts`.
- The TypeScript types, the runtime guard `isOneOf`, and the `CHECK` lists are all generated from those arrays.
- An integration test compares the constraints in the migrated database with the arrays.
- PostgreSQL remains the authority: validation in the application never replaces a constraint.

**Introducing a value:** add it to the array and run `pnpm db:generate`. This writes a migration that drops the constraint and adds it again with the wider list. Then review the migration and commit it.

**Removing or renaming a value:** first migrate the rows that use it, in a reviewed migration, then narrow the constraint.

*Alternative:* native enums (`pgEnum`). They were rejected for three reasons:

- a value added to a native enum cannot be used in the same transaction that adds it;
- removing or renaming a value requires recreating the type;
- the value lists here are small and rarely change.

### 2. Column naming, keys, and time

- Table and column names are `snake_case`, written out explicitly in the Drizzle schema rather than derived by a casing option, so the schema reads the same as the SQL.
- Primary keys of entities are `uuid`, generated by PostgreSQL with `gen_random_uuid()`. ADR 0002's tie-break, "the lowest entry `id`", is therefore deterministic but arbitrary, which is all it needs to be.
- Timestamps are `timestamptz` with database defaults (`now()`). Drizzle sets `updated_at` to `now()` on the updates it issues.
- Constraints are named, so a violation names the rule that was broken.

### 3. Published slugs stay reserved after permanent deletion

1. **Never reassigned.** A slug that has ever identified publicly visible writing is never assigned to other writing, including after the entry is permanently deleted.
2. **Mechanism:**
   - `entry_slugs.was_published` marks such slugs. It is set on the current slug when a language version is published, and on a new slug chosen while the entry is publicly visible.
   - The foreign key from `entry_slugs` to `entries` is `ON DELETE RESTRICT`, so an entry that owns slugs cannot be deleted by accident.
   - "Delete now" runs one transaction. It deletes the entry's never-published slugs, then retires its published ones by clearing `entry_id` and `is_current`, then deletes the entry.
   - A `CHECK` allows only published, non-current slugs to be retired.
   - The existing primary key `(kind, slug)` then keeps a retired slug reserved, with no extra table or trigger.
3. **Minimal retention.** A retired row keeps the entry kind, the slug text, the flag, and its creation time: nothing else. None of the entry's text, translations, ratings, reflections, or links is retained to reserve the URL. The retained slug text was already public, as part of a published URL.
4. **Never-public slugs are released.** Slugs that never identified published writing are deleted with the entry and may be used again.
5. **No disclosure.** A retired slug resolves exactly like an unknown slug (404). It never redirects and reveals nothing about the deleted entry.
6. **Redirects keep respecting visibility.** A previous slug redirects (308) only while its entry is publicly visible (ADR 0002, INV-5). An explicit slug change keeps the old slug, so a previously published URL keeps working while its destination exists and is public.

*Privacy review:*

- **What is retained:** a retired slug is derived from a title the author once published. Retaining it keeps public text, not private writing.
- **What is removed:** title-derived slugs that were never public are deleted.
- **Cost:** a deleted entry's published slug can never be used again for that kind of entry.

*Alternatives considered:*

- **Release every slug** (the original proposal). It was rejected because an old link could lead to unrelated writing.
- **A separate table of retired slugs.** It was rejected because uniqueness across two tables needs a trigger.
- **`ON DELETE SET NULL (entry_id)`.** It was rejected because Drizzle cannot declare it, and it would still need the transaction to remove never-public slugs.

### 4. Publication history is recorded per language version and per entry

- **Current visibility** is `entry_texts.status` and `entry_texts.published_at`. `published_at` is cleared by unpublishing and set anew by publishing again. Featured resolution orders by it (ADR 0002, D1.2).
- **Publication history** is `entry_texts.first_published_at`: when that language version was first published.
  - It is `NULL` for a version that has never been published, such as a draft or private translation.
  - It is set once by the version's first publication.
  - Unpublishing and republishing never change it.
  - Constraints require it while the version is published, and require it to be no later than `published_at`.
- `entries.first_published_at` is the earliest `first_published_at` of any version. It freezes the slug (ADR 0002, D7.4), and it is never cleared.
- The transitions are transactional commands: `publishLanguageVersion` and `unpublishLanguageVersion`. They lock the entry, refuse deleted entries, keep both levels consistent, and mark the current slug as published.
- A `CHECK` constraint cannot see a column's previous value, so "never overwritten" and "equals the earliest version's" are guaranteed by these commands and covered by tests, not by constraints.

### 5. Deferred: restore behavior and purge

- **Restore behavior** does not affect the schema. Restoring clears `entries.deleted_at`, and each language version keeps its stored status. Whether the restore command should also move published versions to private is decided with the Recently deleted feature (M2).
- **Automatic purge** stays disabled (ADR 0002, D4.4). Nothing in the schema purges: no trigger, rule, or scheduled job. The only permanent deletion is the author's explicit "Delete now". The purge mechanism is decided once its preconditions are met.

## Consequences

**Positive**

- Allowed values change through ordinary, reviewable migrations, from one source of values.
- A published URL never leads to unrelated writing, and permanent deletion keeps nothing of the writing except slugs that were already public.
- A deletion that forgets to handle slugs fails instead of silently releasing them.
- Current visibility and publication history are separate, per language version.

**Negative**

- `CHECK` value lists exist in SQL migrations and in TypeScript; the consistency test keeps them aligned.
- Permanent deletion must go through `permanentlyDeleteEntry`; a raw `DELETE FROM entries` is refused for an entry that owns slugs.
- Some rules depend on the commands rather than on constraints, because constraints cannot see previous values or other tables:
  - the publication history is never overwritten;
  - the entry-level history equals the earliest version's;
  - `was_published` is set whenever a slug becomes public.
- A published slug of a deleted entry can never be reused, even by the author.
- `updated_at` is maintained by Drizzle and the commands, not by a trigger, so a raw SQL `UPDATE` must set it explicitly.

## Revisit when

- a value list starts changing often;
- writes start bypassing the module commands;
- a reason appears to free a published slug, for example an explicit, separately confirmed author action.
