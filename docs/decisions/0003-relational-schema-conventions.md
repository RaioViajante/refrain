# ADR 0003: Relational Schema Conventions

- **Status:** Proposed. Implemented in M1.2 (issue #4, pull request #5) and awaiting the author's acceptance in that pull request's review.
- **Date:** 2026-10-31
- **Scope:** How the first migration represents ADR 0002, and the open questions from [ADR 0002](0002-domain-model-decisions.md#still-open-after-this-adr) and [Data Model](../data-model.md#open-questions) that the schema depends on. It does not change any decision in ADR 0002.

## Context

ADR 0002 left three questions open, and the [Roadmap](../roadmap.md) asked M1.2 to settle the ones that affect the first migration:

1. How enumerations are represented in PostgreSQL.
2. Whether a slug is released when an entry is permanently deleted.
3. Whether published language versions return as private when a deleted entry is restored.

The preliminary data model also left two details to the implementation: Drizzle's column-naming convention, and where the first-publication time lives. Migrations are permanent once applied, so these are settled before the first one.

## Decision

### 1. Enumerations are `text` with `CHECK` constraints

Entry kind, locale, visibility status, and artist kind are `text` columns with a named `CHECK` constraint listing the allowed values, as the data model already showed. TypeScript gets the same value lists through Drizzle's `text(..., { enum })`.

*Alternative:* native enums (`pgEnum`). Adding a value to a native enum cannot be used in the same transaction that adds it, removing or renaming a value requires recreating the type, and the value lists here are small and rarely change. A `CHECK` constraint is altered with an ordinary migration.

### 2. Column naming, keys, and time

- Table and column names are `snake_case`, written out explicitly in the Drizzle schema rather than derived by a casing option, so the schema reads the same as the SQL.
- Primary keys of entities are `uuid`, generated by PostgreSQL with `gen_random_uuid()`. ADR 0002's tie-break, "the lowest entry `id`", is therefore deterministic but arbitrary, which is all it needs to be.
- Timestamps are `timestamptz` with database defaults (`now()`). Drizzle sets `updated_at` to `now()` on updates it issues.
- Constraints are named, so a violation names the rule that was broken.

### 3. A slug is released when its entry is permanently deleted

`entry_slugs` rows cascade with their entry (`ON DELETE CASCADE`). While the entry exists, including in Recently deleted, its current and previous slugs stay reserved (ADR 0002, D7.5). After "Delete now", they are free to be used again.

*Alternative:* keep reserved slugs as tombstones after deletion. Slugs are derived from titles, so a tombstone would keep a fragment of writing the author asked to remove permanently. The risk accepted instead is that an old external link to a permanently deleted entry could later lead to a new entry with the same slug.

### 4. The first publication is recorded on the entry

`entries.first_published_at` is set once, when any language version is first published, and is never cleared by unpublishing. ADR 0002, D7.4 freezes the slug "until the entry is first published", which is a fact about the entry rather than about one language version. The preliminary data model placed this column on `entry_texts`.

### 5. Deferred: restore behavior and purge

- **Restore behavior** does not affect the schema: restoring clears `entries.deleted_at`, and each language version keeps its stored status. Whether the restore command should also move published versions to private is decided with the Recently deleted feature (M2).
- **Automatic purge** stays disabled (ADR 0002, D4.4). Nothing in the schema purges: no trigger, scheduled job, or time-based constraint. Its mechanism is decided once its preconditions are met.

## Consequences

**Positive**

- Allowed values can change through ordinary, reviewable migrations.
- Constraint names in errors and tests correspond to rules in the documentation.
- Permanent deletion leaves no derived trace of the deleted writing.

**Negative**

- `CHECK` value lists are repeated in SQL and in TypeScript. Integration tests that write invalid values keep them consistent.
- A released slug can be reused, so a very old link may lead to different writing.
- `updated_at` is maintained by Drizzle, not by a trigger, so a raw SQL `UPDATE` must set it explicitly.

## Revisit when

A value list starts changing often, a public URL needs to survive permanent deletion, or writes start bypassing Drizzle.
